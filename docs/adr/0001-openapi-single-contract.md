# 0001. API 계약은 OpenAPI 하나로 두고 Go 타입은 생성한다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

플랫폼 API를 부르는 쪽이 셋이다. 웹 콘솔(TypeScript), `charlie` CLI(Go, 별도 레포), AI 플래너다. 지금까지는 엔진 상태 구조체를 그대로 JSON으로 내보냈다. 그래서 응답 형식이 엔진 내부 구조에 묶여 있었고, 콘솔과 CLI가 같은 형식을 보고 있다는 보장이 없었다.

## 결정

- `api/openapi.yaml`을 유일한 계약으로 둔다. 서버, CLI, 콘솔이 모두 이 파일을 기준으로 삼는다.
- Go 타입은 oapi-codegen으로 `pkg/apiv1`에 생성한다. 생성기 버전은 go.mod의 `tool` 지시어로 고정하고, `go generate ./pkg/apiv1`로 누구나 같은 결과를 만든다.
- CLI는 별도 `cli` 레포에 두고 `platform/pkg/apiv1`과 `platform/pkg/client`를 import한다.
- 콘솔은 같은 파일에서 `npx openapi-typescript api/openapi.yaml -o src/api/types.ts`로 타입을 만든다.
- 서버는 엔진 상태를 그대로 내보내지 않고 `Run` 문서로 감싼다. 엔진 상태는 `Run.engine`에 들어간다.
- 서버 테스트는 모든 응답을 이 명세로 검증한다(kin-openapi). 명세와 구현이 어긋나면 테스트가 실패한다.

## 검토한 대안

- Go 구조체를 먼저 쓰고 명세를 생성하는 방식: Go 쪽은 편하지만, 콘솔 개발자가 Go 코드를 읽어야 계약을 알 수 있다. 생성 도구도 주석 규칙이 제각각이다.
- 생성 없이 명세와 Go 타입을 손으로 맞추는 방식: 처음에는 빠르지만 일주일 안에 어긋난다. 응답 검증 테스트로 일부 막을 수 있지만, 타입 이름과 필드 이름까지 맞추는 일은 사람이 해야 한다.
- CLI를 platform 레포 안에 두는 방식: 타입 공유는 가장 쉽다. 하지만 CLI 배포 주기와 플랫폼 배포 주기가 묶이고, 콘솔과 같은 위치(바깥 클라이언트)에 있다는 점이 흐려진다.

## 결과

- 필드를 바꾸려면 명세를 먼저 고쳐야 한다. 대신 바꾼 내용이 세 클라이언트에 같이 반영된다.
- 생성 타입은 선택 필드가 포인터다. 쓰는 쪽 코드가 조금 길어진다.
- CLI 레포는 platform 모듈 버전을 따라가야 한다. 플랫폼 PR이 머지되면 CLI의 go.mod를 올린다.
