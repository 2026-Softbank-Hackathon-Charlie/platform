# 0018. 사람은 관리자 계정으로 로그인하고, CLI는 콘솔에서 승인받는 device code로 토큰을 받는다

- 상태: 채택
- 날짜: 2026-11-04

## 상황

ADR 0003은 모든 호출자가 `PLATFORM_TOKENS`의 정적 토큰을 쓰게 했다. 사람도 토큰 문자열을 받아 콘솔에 붙여 넣거나 CLI 설정 파일에 넣는다. 그래서 이런 문제가 있다.

- 토큰은 만료되지 않는다. 노트북이나 채팅 기록에 남은 토큰은 서버의 `PLATFORM_TOKENS`를 바꾸고 다시 띄우기 전까지 계속 쓸 수 있다.
- 토큰을 하나 더 주거나 회수하려면 서버 환경 변수를 바꿔야 한다.
- 콘솔 첫 화면이 토큰을 붙여 넣는 칸이라, 심사위원이나 새로 온 운영자가 쓰기 어렵다.
- CLI는 원격 서버의 SSH 세션에서도 쓴다. 그리고 AI 봇 Rin은 실행마다 새 컨테이너에서 CLI를 돌린다. 둘 다 브라우저를 열 수 없고, Rin은 한 단계가 끝나면 컨테이너가 사라진다. 지금은 정적 토큰을 미리 넣어 두는 수밖에 없어서, 누가 언제 그 권한을 허락했는지 남지 않는다.

## 결정

### 관리자 계정과 콘솔 로그인

- 관리자는 `PLATFORM_ADMINS="이름:bcrypt 해시,..."`로 넣는다. 이름 규칙은 토큰 이름과 같다. 로그인할 때 이름의 대소문자는 가리지 않으므로, 대소문자만 다른 두 이름은 넣을 수 없다. 관리자는 모두 operator다.
- 해시는 `hopcharlie-api -hash-password`(`go run ./cmd/api -hash-password`)로 만든다. 표준 입력에서 비밀번호 한 줄을 읽고(터미널이면 화면에 보이지 않게), cost 12의 bcrypt 해시를 출력하고 끝난다. DB나 토큰 설정 없이 동작한다. bcrypt는 72바이트까지만 읽으므로 그보다 긴 비밀번호는 거부한다.
- 서버는 시작할 때 해시가 bcrypt 형식인지 확인하고, 아니면 시작하지 않는다. 오류 메시지에는 해시를 넣지 않는다. 형식이 틀린 항목은 내용 대신 몇 번째 항목인지로 알린다.
- `POST /v1/auth/login {username, password}`가 맞으면 콘솔 세션 토큰을 준다. 틀린 비밀번호와 없는 이름은 같은 401 `invalid_credentials`로 답한다. 없는 이름도 같은 cost의 가짜 해시와 한 번 비교해서, 응답 시간으로 이름이 있는지 알 수 없게 한다.
- 이름마다 시도를 센다. 10분 안에 10번 실패하면 429 `too_many_attempts`로 답하고, `Retry-After`에 가장 오래된 실패가 10분 창을 벗어날 때까지 남은 초를 넣는다. 막힌 동안에는 비밀번호를 비교하지 않는다.
  - 시도는 비밀번호를 비교하기 전에 센다. 동시에 보낸 요청도 한도를 넘지 못한다. 로그인에 성공하면 그 이름의 기록을 지우므로, 남는 것은 실패뿐이다.
  - 이름은 소문자로 바꿔 센다.
  - 기록은 API 서버 메모리에 두고, 이름 1만 개까지만 기억한다. 가득 차면 10분 창을 벗어난 이름부터 지우고, 그래도 차 있으면 마지막 시도가 가장 오래된 이름을 지운다. 아무 이름이나 뿌리는 요청이 메모리를 끝없이 늘리지 못한다.
- 로그인 라우트는 토큰이 없어서 핸들러가 직접 감사 로그를 쓴다(GitHub webhook과 같은 방법). 성공은 관리자 이름과 operator로 남기고, 실패와 429는 시도한 이름으로 남긴다. 시도한 이름이 이름 규칙에 맞지 않으면 `anonymous`로 남긴다. 비밀번호는 서버 로그와 감사 로그 어디에도 남기지 않는다. 형식이 틀린 요청(400)과 관리자가 없는 서버의 503은 시도로 보지 않아 남기지 않는다.

### CLI의 device code 로그인

RFC 8628(OAuth device authorization grant)의 흐름을 따른다.

1. CLI가 `POST /v1/auth/device {client}`를 보낸다. `client`는 `charlie v0.5.0 on rin-sbx-12`처럼 무엇이 요청하는지 적은 문자열이고, 관리자가 승인하기 전에 이것을 본다. 서버는 `deviceCode`(CLI만 아는 비밀), `userCode`(`BCDF-GHJK`처럼 넷씩 두 묶음인 8글자), `verificationUri`(`PLATFORM_CONSOLE_URL` 뒤에 `/#device`), `expiresIn` 600, `interval` 5를 준다.
2. CLI는 사람에게 `userCode`와 주소를 보여 준다. 관리자는 콘솔에 로그인한 상태로 그 주소에서 코드를 넣고, `client`를 확인한 뒤 CLI 토큰의 역할을 골라 승인하거나 거절한다. `GET /v1/auth/device/{userCode}`, `POST .../approve {role}`, `POST .../deny`이다.
3. CLI는 `interval`초마다 `POST /v1/auth/device/token {deviceCode}`를 보낸다. 승인 전에는 400 `authorization_pending`, 거절됐으면 400 `access_denied`(그 기기 로그인은 지워진다), 모르거나 만료됐거나 이미 토큰으로 바꾼 코드는 400 `expired_token`이다. 승인된 뒤 첫 요청이 CLI 토큰을 받는다. 토큰에는 승인한 관리자의 이름과, 승인할 때 고른 역할이 들어간다.

- 모든 단계가 평범한 HTTP 요청이다. CLI 쪽에는 브라우저도, 콜백을 받을 포트도 필요 없다. 시작과 폴링 사이에 이어지는 상태는 `deviceCode` 하나뿐이다. Rin처럼 단계마다 새 컨테이너에서 도는 경우에도, 앞 단계가 받은 `deviceCode`만 다음 단계에 넘기면 폴링을 이어 갈 수 있다.
- `userCode`는 모음과 숫자처럼 보이는 글자를 뺀 20글자(`BCDFGHJKLMNPQRSTVWXZ`)에서 crypto/rand로 고르게 뽑는다. 경우의 수는 20^8(약 256억)이다. 저장할 때는 `-` 없이 두고, 보여 줄 때만 `XXXX-XXXX`로 쓴다. 입력할 때 대소문자, 공백, `-`는 무시한다. 살아 있는 기기 로그인과 코드가 겹치면 다시 뽑는다.
- 승인과 거절은 콘솔 세션, 즉 비밀번호로 로그인한 관리자만 한다. 정적 토큰과 CLI 토큰은 operator여도 403 `console_session_required`다. 조회(`GET`)도 같다. 두 가지 이유다.
  - Rin 같은 봇이 operator CLI 토큰을 가지고 있어도, 자기의 다음 기기 로그인을 스스로 승인해 새 토큰을 계속 만들 수 없다. CLI 토큰은 사람이 승인해야만 생긴다.
  - 승인은 비밀번호를 아는 사람의 결정이어야 한다. 프로그램용 정적 토큰으로 승인하면 누가 허락했는지가 사람 이름으로 남지 않는다.
- 승인할 때 `role`(viewer, agent, operator)을 반드시 고른다. 빠지거나 모르는 값이면 400 `invalid_request`다. CLI 토큰은 승인한 관리자의 역할(operator)이 아니라 이 역할을 받는다. 봇에는 필요한 만큼만 준다. 읽기만 하면 viewer, Plan을 제출하면 agent이고, Rin처럼 대화로 움직이는 봇은 배포나 승인을 직접 해야 할 때만 operator를 준다. AI가 승인과 실행까지 하지 못하게 한다는 0003의 원칙이 CLI 토큰에서도 그대로 지켜진다.
- 승인과 거절은 pending일 때만 된다. 아니면 409 `device_login_state_conflict`다. 승인하면 승인한 사람의 이름, 시각, 고른 역할을 기록하고, 응답의 `DeviceLogin.role`로 돌려준다.
- 승인하면 교환 기한을 늘린다. 만료 시각을 지금 만료 시각과 승인 시각 뒤 10분 중 늦은 쪽으로 바꾸고, 응답의 `expiresAt`도 바뀐 값이다. Rin은 사람이 승인하는 동안 폴링을 멈췄다가 다음 실행에서 `charlie login`을 다시 돌려 폴링하는데, 기기 로그인을 시작하고 9분 뒤에 승인되면 원래 기한으로는 1분 안에 다시 돌아와야 한다. 늘린 기한 안이면 늦게 와도 토큰을 받는다. 거절은 기한을 바꾸지 않는다.
- 토큰 교환은 한 번만 일어난다. 기기 로그인 행을 지우는 조건부 쓰기와 CLI 세션 생성을 한 트랜잭션으로 하므로, 두 폴링이 동시에 와도 토큰은 하나만 나간다.
- 만료되지 않은 pending 기기 로그인은 50개까지다. 넘으면 429 `too_many_attempts`, `Retry-After: 60`이다. 시작 요청은 토큰 없이 아무나 보낼 수 있어서 상한을 둔다. 만료된 행은 다음 시작 요청이 지운다.
- 감사 로그: 승인과 거절은 다른 operator 요청처럼 남고 `userCode`, `client`를 덧붙인다. 승인에는 고른 역할(`tokenRole`)도 덧붙인다. 토큰 교환은 승인한 관리자를 actor로, 고른 역할을 role로 하고 `client`, `userCode`를 덧붙인다. 시작 요청과 승인 전 폴링은 결정이 아니므로 남기지 않는다. `deviceCode`와 토큰은 어떤 응답이나 기록에도 다시 나오지 않는다.
- CLI 토큰으로 한 요청의 감사 로그는 actor가 승인한 관리자이고, detail의 `via`에 그 토큰을 받은 CLI의 `client`가 들어간다. 예를 들어 seohyun이 승인한 토큰으로 Rin이 Plan을 제출하면 actor `seohyun`, role `agent`, `via` `charlie v0.5.0 on rin-sbx-7-a1b2c3`으로 남는다. 누가 허락했고 어느 프로그램이 했는지가 한 줄에 같이 보인다. 콘솔 세션과 정적 토큰의 요청에는 `via`가 없다. 토큰 자체는 남기지 않는다.

### 토큰 종류와 수명

| 종류 | 받는 방법 | 이름과 역할 | 수명 |
| --- | --- | --- | --- |
| 콘솔 세션 | `POST /v1/auth/login` | 관리자 이름, operator | 12시간 |
| CLI 토큰 | 승인된 기기 로그인을 `POST /v1/auth/device/token`으로 교환 | 승인한 관리자의 이름, 승인할 때 고른 역할 | 30일 |
| 정적 토큰 | `PLATFORM_TOKENS` | 설정한 이름과 역할 | 없음 |

- 콘솔 세션과 CLI 토큰은 `hcs_` 뒤에 무작위 32바이트를 base64url로 붙인 문자열이다. `POST /v1/auth/logout`으로 바로 끝낼 수 있다. 정적 토큰으로 logout하면 204로 답하지만 토큰은 그대로 쓸 수 있다.
- 세 종류 모두 `Authorization: Bearer`로 보낸다. 서버는 정적 토큰부터 기존처럼 상수 시간으로 비교한다. 맞지 않고 `hcs_`로 시작하는 값만 저장소에서 찾고, 없거나 만료됐으면 401이다. 저장소를 읽지 못하면 401 대신 500으로 답해서, DB 장애로 콘솔이 로그아웃되지 않게 한다.
- 저장소(`auth_sessions`, `device_logins`, 마이그레이션 0007)에는 토큰과 `deviceCode`의 SHA-256만 둔다. DB 내용이 새어도 쓸 수 있는 토큰은 나오지 않는다. 32바이트 무작위 값이라 솔트 없는 SHA-256으로 충분하다.
- 세션 행에는 이름, 역할, 종류(`console`, `cli`), CLI의 `client`(콘솔은 빈 값), 만든 시각, 만료 시각을 둔다. 만료된 행은 다음 세션을 만들 때 지운다. 읽을 때는 만료 시각을 현재 시각과 비교하므로 지우기 전에도 쓸 수 없다.

### 정적 토큰은 프로그램용으로 남긴다

- 로그인할 수 없는 프로그램은 계속 `PLATFORM_TOKENS`를 쓴다. AI 플래너(agent), 부하 생성기, E2E 스크립트다. 토큰 형식과 검사는 바꾸지 않는다.
- 서버는 정적 토큰과 관리자가 모두 없을 때만 시작을 거부한다(`-insecure-no-auth`면 시작한다). 모든 요청을 operator `dev`로 보는 개발 모드도 둘 다 없을 때만 켜진다. 이 모드의 `dev`는 콘솔 세션으로 취급해서 로컬에서 기기 로그인 승인까지 해 볼 수 있다.

### ADR 0003과의 관계

이 ADR은 0003에서 사람이 로그인하는 방법(사람도 정적 토큰을 받는 방식)을 대체한다. 역할 세 가지, 라우트마다의 역할 검사, 감사 로그 규칙은 0003 그대로다.

## 검토한 대안

- OIDC(Google, GitHub) 로그인: 0003에서 미뤘던 방법이다. IdP에 앱을 등록하고 콜백 주소와 조직 제한을 설정해야 하고, 심사위원에게 줄 계정도 IdP 쪽에 있어야 한다. 남은 일정에 비해 크다. 역할 모델과 `/v1/auth` 경계는 그대로 두고 나중에 로그인 방법만 더할 수 있다.
- 콘솔에 정적 토큰을 붙여 넣는 방식 유지: 만료와 회수가 없고, 사람과 프로그램이 같은 종류의 비밀을 쓴다.
- CLI도 아이디와 비밀번호로 로그인: CLI와 Rin에 관리자 비밀번호를 넣어야 한다. Rin의 컨테이너 로그나 대화 기록에 비밀번호가 남을 수 있다. device code에서는 비밀번호가 콘솔 밖으로 나가지 않고, 관리자가 요청마다 무엇에 권한을 주는지 보고 승인한다.
- CLI의 브라우저 로그인(localhost 콜백): 원격 서버, SSH 세션, Rin의 컨테이너에서는 브라우저를 열 수 없고 콜백 포트에 닿을 수 없다.
- 승인한 관리자의 역할을 CLI 토큰에 그대로 주기: 관리자는 모두 operator라서, 봇이 받는 토큰도 언제나 operator가 된다. 읽기만 하는 봇에도 배포와 승인 권한이 생긴다.
- 정적 operator 토큰이나 CLI 토큰으로도 승인하게 두기: CLI 토큰을 가진 봇이 자기 다음 토큰을 스스로 승인할 수 있다. 사람의 승인을 거쳐야 토큰이 생긴다는 전제가 깨진다.
- JWT 같은 서명 토큰: 요청마다 DB를 읽지 않아도 되지만 만료 전에 끝낼 수 없다. logout과 회수를 하려면 결국 차단 목록을 저장해야 한다. 요청마다 기본 키 조회 한 번이면 충분하다.
- 로그인 실패 횟수를 DB에 저장: 재시작해도 남지만 실패마다 쓰기가 생긴다. API 서버는 한 대라 메모리로 충분하다.

## 결과

- 콘솔은 아이디와 비밀번호로 로그인한다. CLI와 Rin은 관리자가 콘솔에서 코드를 승인해야 토큰을 받고, 그 토큰으로 한 일은 승인한 관리자 이름과 `via`로 감사 로그에 남는다.
- CLI 토큰과 정적 operator 토큰으로는 기기 로그인을 승인할 수 없다. 콘솔이 아닌 곳에서 승인하려면 관리자 비밀번호로 `POST /v1/auth/login`을 거쳐 콘솔 세션을 받아야 하므로, 비밀번호를 아는 사람만 승인한다.
- 봇에 operator를 주면 그 토큰으로 배포와 Plan 승인까지 할 수 있다. 그래서 승인하는 사람이 매번 역할을 직접 고르게 했다(요청 본문의 `role`은 필수다).
- 관리자를 더하거나 비밀번호를 바꾸려면 여전히 `PLATFORM_ADMINS`를 바꾸고 서버를 다시 띄워야 한다. 관리자를 빼거나 비밀번호를 바꿔도 이미 나간 세션과 CLI 토큰은 만료될 때까지 유효하다. 바로 끊어야 하면 그 토큰으로 logout하거나 `auth_sessions`에서 행을 지운다.
- 로그인 실패 기록은 메모리에 있어서 서버를 다시 띄우면 지워진다. API 서버를 여러 대로 늘리면 대마다 따로 센다.
- 누군가 관리자 이름으로 일부러 10번 틀리면 그 관리자도 최대 10분 동안 로그인하지 못한다. 그동안은 다른 관리자 계정이나 이미 받은 CLI 토큰을 쓴다.
- 이름별 제한은 한 계정에 대한 추측을 막지만, 여러 이름으로 보내는 대량 요청은 막지 않는다. 없는 이름도 cost 12 비교를 하므로 그런 요청은 CPU를 쓴다. 문제가 되면 IP 단위 제한을 앞단에 더한다.
- 시작 요청에는 인증이 없으므로, 누군가 pending 기기 로그인 50개를 계속 채우면 CLI 로그인이 429로 막힌다. 그때도 IP 단위 제한을 더한다.
- 콘솔은 쿠키가 아니라 `Authorization` 헤더로 세션을 보낸다. CSRF는 걱정하지 않아도 되지만, 콘솔 페이지의 XSS는 곧 세션 탈취다. 12시간 수명과 logout이 노출 기간을 줄인다.
- 429 응답의 `Retry-After`를 CORS `Access-Control-Expose-Headers`에 넣어 콘솔이 읽을 수 있게 했다.
