# 0011. GitHub 저장소로 앱을 등록하고, 플랫폼이 빌드해 gitops 저장소에 커밋하면 Argo CD가 배포한다

- 상태: 채택
- 날짜: 2026-11-03
- 이후 바뀐 점: 서비스의 `port`를 생략할 수 있게 하고(워커), `memory`, `cpu`와 DB 연결 변수의 예약 이름을 더했다. [ADR 0024](0024-service-contract-workers-resources-db-env.md)를 본다.

## 상황

지금까지 플랫폼은 이미 떠 있는 앱의 데이터를 환경 사이에서 옮기기만 했다. 앱을 처음 띄우는 일은 사람이 했고, 앱 목록(`PLATFORM_APPS_FILE`)도 사람이 고쳤다. 본선 데모는 GitHub 저장소 하나로 앱을 등록하고, push 할 때마다 여러 환경에 배포되고, 그 앱을 이전하는 흐름까지 보여 줘야 한다. 콘솔, CLI, 배포 실행기, infra를 동시에 만들기 때문에 계약을 먼저 정해야 했다.

## 결정

### 앱 저장소 계약

- 앱 저장소에는 서비스마다 Dockerfile 하나, 저장소 루트에 `platform.yaml` 하나를 둔다.

  ```yaml
  name: moimroom              # 네임스페이스, Application, 이미지 경로, URL에 쓰는 이름
  services:                   # 1개에서 5개
    - name: web
      path: .                 # 빌드 컨텍스트 (기본 .)
      dockerfile: Dockerfile  # path 기준 (기본 Dockerfile)
      port: 8080
      healthCheck: /healthz
      public: true            # https://moimroom.hopcharlie.dev, 하나까지
      replicas: 1             # 기본 1, 최대 5
      env: {LOG_LEVEL: info}
  resources:                  # 종류마다 하나까지
    - {name: db, type: postgres}
    - {name: photos, type: s3}
  ```

- 규칙은 `pkg/appspec`이 검사하고, CLI도 같은 패키지를 쓴다. 모르는 키는 오류다. 이름은 `^[a-z0-9]([a-z0-9-]{0,30}[a-z0-9])?$`, 서비스와 리소스 이름은 `<app>-<name>`에 접미사가 붙어도 63자 안에 들도록 `^[a-z]([a-z0-9-]{0,22}[a-z0-9])?$`이다. `path`와 `dockerfile`은 상대 경로이고 `..`를 쓸 수 없다.
- env 키는 `^[A-Z_][A-Z0-9_]*$`이고, 플랫폼이 넣는 변수는 쓸 수 없다. YAML이 숫자, 불리언, null로 읽는 값(`4`, `yes`, `0755`, `~`)은 오류다. 그대로 받으면 `0755`가 `493`으로 바뀌어 앱에 들어가기 때문이다.
- 플랫폼(차트)이 넣는 변수는 다음과 같다.
  - 모든 서비스에 `PORT`.
  - `postgres` 리소스는 CNPG Cluster `<app>-<resource>`가 되고, 그 secret `<app>-<resource>-app`의 `uri`가 `DATABASE_URL`이 된다.
  - `s3` 리소스는 `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_PATH_STYLE`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`를 넣는다. `S3_` 접두사 전체를 예약한다.

### 등록과 트리거

- operator가 `POST /v1/apps`로 저장소, 브랜치, 대상 환경을 보낸다. 플랫폼은 GitHub App으로 브랜치 head의 `platform.yaml`을 읽어 검사하고(각 서비스의 Dockerfile이 있는지도 본다), 앱을 PostgreSQL에 저장하고, 첫 배포(trigger `register`)를 큐에 넣는다. 앱 이름은 `platform.yaml`의 `name`이다.
- `api`, `console`과 게이트웨이의 기본 앱 이름 `app`은 플랫폼이 `hopcharlie.dev` 아래에서 직접 쓰므로 등록할 수 없다(409 `app_exists`, ADR 0012).
- `PLATFORM_APPS_FILE`의 앱(이전용)은 그대로 둔다. 파일에만 있는 이름은 등록을 막지 않는다. 같은 이름이 양쪽에 있으면 `GET /v1/apps`는 파일의 항목에 `deploy`를 붙여 한 번만 보여 준다. 등록만 된 앱은 `namespace`가 이름, `database`가 CNPG 기본값 `{name: app, user: app}`, `environments`가 빈 목록이다.
- 배포는 GitHub App의 push webhook(등록한 브랜치, `autoDeploy`)이나 수동 배포(`POST /v1/apps/{name}/deployments`)로 시작한다. webhook은 bearer 토큰 대신 `X-Hub-Signature-256` HMAC으로 확인하고, `X-GitHub-Delivery`로 다시 온 배달을 거른다. push가 아닌 이벤트와 관계없는 push는 204로 답한다.
- `platform.yaml`이 잘못되면 422 `invalid_app_spec`이다. 본문은 `Error`에 `validation`(`AppSpecValidation`)을 더한 `AppSpecInvalid`다.

### 빌드와 배포

- 운영은 AWS CodeBuild, E2E는 로컬 docker로 빌드한다. 서비스마다 `<registry>/hopcharlie/apps/<app>/<service>:<commit>`으로 push하고, gitops에는 digest로 고정한 이미지(`...@sha256:...`)를 쓴다.
- 플랫폼은 `2026-Softbank-Hackathon-Charlie/gitops` 저장소에 `apps/<app>/<env>.yaml`을 커밋하고 Argo CD에 refresh를 요청한다. infra 저장소의 ApplicationSet(git files generator, `apps/*/*.yaml`)이 Application `<app>-<env>`를 infra의 차트 `helm/charts/hopcharlie-app`으로 만든다. 환경 프로필 값은 infra에 있고, 네임스페이스는 앱 이름이다.
- Git이 원하는 상태다. 플랫폼은 Application을 직접 만들지 않는다.
- gitops 파일이 차트와의 계약이다. `values`가 차트의 values다.

  ```yaml
  # Generated by the HopCharlie platform. Do not edit.
  app: moimroom
  env: eks
  namespace: moimroom
  commit: <git sha>
  deployment: <deployment id>
  values:
    app: moimroom
    services:
      - {name: web, image: "<repo>@sha256:...", port: 8080, healthCheck: /healthz, public: true, replicas: 1, env: {KEY: value}}
    resources:
      - {name: db, type: postgres}
      - {name: photos, type: s3}
  ```

- `public: true` 서비스는 traffic gateway가 `https://<app>.hopcharlie.dev`로 내보낸다. 호스트 라우팅은 따로 만드는 중이다.

### 상태, 저장소, 실행기

- 배포 상태는 `queued`, `building`, `committing`, `syncing`을 거쳐 `healthy`, `failed`, `superseded` 중 하나로 끝난다. 환경마다 `pending`, `syncing`, `healthy`, `degraded`, `failed`를 따로 둔다.
- `healthy`는 모든 환경의 Application이 `Synced`, `Healthy`라는 뜻이고, 게이트웨이가 설정되어 있고 공개 서비스가 있으면 게이트웨이가 요청을 보내는 환경(쓰기 백엔드와 읽기 가중치가 있는 백엔드)의 백엔드 주소에서 서비스가 실제로 답한다는 뜻이기도 하다. 실행기는 `healthCheck`(없으면 `/`)를 불러 답을 받은 환경만 게이트웨이에 넣거나 바꾸고, 같은 주소로 이미 들어 있는 환경은 다시 부르지 않는다. Argo CD는 LoadBalancer Service에 주소가 생기면 바로 `Healthy`로 보지만 AWS NLB는 그 뒤에도 몇 분 동안 만들어지는 중이라, 2026-11-04 moimroom의 첫 배포는 `healthy`로 끝난 뒤 2분쯤 게이트웨이가 502를 답했다. 답을 기다리는 시간도 커밋 때 시작한 같은 제한 시간 안이다. 그 안에 요청을 받는 환경이 답하지 않으면 게이트웨이를 바꾸지 않고 `failed`로 끝난다. 그 밖의 환경은 요청을 받는 환경이 모두 답한 뒤 `PollInterval` 두 번까지만 더 기다리고, 그때까지 답하지 않으면 그 환경만 게이트웨이 갱신에서 빠지고 환경 `message`에 이유가 남는다(다음 배포에서 다시 확인). 요청을 받지 않는 환경 하나 때문에 worker가 마감까지 묶이지 않게 하려는 것이다. 알려진 한계: 게이트웨이 쪽 DNS가 답을 받기 전의 '이름 없음'을 잠시 캐시하면 등록 직후에도 짧게 502가 날 수 있고, 기다리는 동안 배포 worker 하나를 차지한다.
- 새 배포가 생기면, 대상 환경이 모두 새 배포에 들어가는 끝나지 않은 이전 배포는 `superseded`가 된다. `UpdateDeployment`는 끝난 배포를 바꾸지 않고 `ErrConflict`를 돌려주므로, superseded 된 배포의 작업자는 다음 쓰기에서 멈추고 새 배포보다 늦게 gitops에 커밋하지 않는다.
- 저장소는 `apps`, `deployments`, `deployment_events`, `webhook_deliveries` 네 테이블이다(마이그레이션 `0005_app_deploy.sql`). 메서드는 `store.DeployStore`에 있고 `store.Store`에 들어 있다.
- 배포 이벤트는 run 이벤트와 같은 SSE 규칙(처음과 끝의 `snapshot`, seq가 SSE id, `Last-Event-ID`로 재접속)을 따른다.
- API는 배포를 저장한 뒤 `api.Deployer`의 `Enqueue`를 부른다. Deployer가 없는 서버에서는 배포가 `queued`로 남는다. 서버가 재시작하면 실행기는 `ListUnfinishedDeployments`로 끝나지 않은 배포를 이어 간다. 이전(run)과 달리 사람 승인 단계가 없고, 같은 커밋을 다시 빌드하고 커밋해도 결과가 같기 때문이다.

## 검토한 대안

- 플랫폼이 Application을 직접 만드는 방식: 빠르지만 원하는 상태가 플랫폼 DB에만 남는다. 클러스터를 다시 만들면 복구할 근거가 없다. Git에 두면 Argo CD가 다시 맞추고, infra의 ApplicationSet 하나로 모든 앱을 같은 차트로 만든다.
- 앱 저장소에 Helm 차트나 매니페스트를 두는 방식: 앱마다 자유롭지만 DB와 버킷 주입, NetworkPolicy, 게이트웨이 연결을 플랫폼이 보장할 수 없다. `platform.yaml`은 플랫폼이 책임질 수 있는 만큼만 받는다.
- 앱 저장소의 GitHub Actions로 빌드하는 방식: 저장소마다 워크플로와 레지스트리 자격 증명을 넣어야 한다. 플랫폼이 CodeBuild를 부르면 등록만으로 끝난다.
- 이미지를 태그로 가리키는 방식: 같은 태그를 다시 push하면 내용이 바뀐다. digest로 고정하면 gitops 커밋 하나가 이미지 하나를 정확히 가리킨다.
- 422에 `AppSpecValidation`만 보내는 방식: 오류는 항상 `Error` 형식이라는 규칙(0001)이 깨지고, 콘솔과 CLI의 공통 오류 처리가 `code`를 읽지 못한다.

## 결과

- 배포 기록은 플랫폼 DB에, 원하는 상태는 Git에 남는다. 둘이 어긋나면 Git이 맞다.
- 앱을 지우면 gitops 파일이 지워지고 Argo CD가 Application과 그 리소스를 지운다. DB의 데이터도 함께 사라지고 되돌릴 수 없다.
- 버전 1은 리소스를 종류마다 하나만 받는다. 둘 이상 받으려면 변수 이름 규칙(예: `DATABASE_URL_<NAME>`)을 먼저 정해야 한다.
- `platform.yaml`은 git에 있으므로 env에 비밀값을 넣지 않는다. 비밀값 주입은 아직 없다.
- 이 레포 밖에서 infra가 맡는 일:
  - ApplicationSet과 차트 `helm/charts/hopcharlie-app` (위 gitops 파일의 `values`를 받는다)
  - CodeBuild 프로젝트와 IAM (ECR push, 플랫폼 pod 역할의 빌드 시작 권한)
  - Argo CD sync 정책과 플랫폼이 refresh를 요청할 권한
  - DNS `*.hopcharlie.dev`, 앱 네임스페이스의 NetworkPolicy
