# 0012. 게이트웨이는 호스트 이름으로 앱을 고르고, 앱마다 라우팅과 쓰기 보류를 따로 둔다

- 상태: 채택
- 날짜: 2026-11-03

## 상황

플랫폼이 곧 GitHub에서 여러 앱을 배포한다. 앱마다 `https://<app>.hopcharlie.dev`로 서빙하고, 공용 ALB는 `*.hopcharlie.dev`를 게이트웨이 하나로 보낸다. 지금 게이트웨이는 앱 하나만 안다(`-backends`, 상태 파일 하나, `/v1` 관리 API). 앱을 하나씩 따로 이전하려면 앱마다 환경, 쓰기 환경, 읽기 비율, 쓰기 보류, 통계가 따로 있어야 한다. 한편 이전 흐름(엔진, `internal/runs`, E2E)과 infra의 Helm 차트는 지금 동작에 맞춰져 있어서, 지금 설정은 그대로 동작해야 한다.

## 결정

- 지금 설정을 기본 앱으로 둔다. `-backends`, 상태 파일의 최상위 필드, `/v1` 관리 API, `gateway.Client`의 기존 메서드, 기존 지표가 모두 기본 앱이다. 새 플래그 `-app-domain`의 기본값은 비어 있고, 비어 있으면 모든 요청이 기본 앱으로 가서 지금과 같다.
- 앱 하나는 라우터 하나다. 라우터마다 잠금, 보류 세대, 처리 중인 쓰기 수, 통계가 따로 있다. 그래서 한 앱의 hold는 다른 앱의 처리 중인 쓰기를 기다리지 않고, 다른 앱의 새 쓰기를 붙잡지도 않는다. 라우팅과 hold의 코드는 앱 하나일 때의 것을 그대로 쓴다.
- `Host`가 `<app>.<domain>`(대소문자와 포트 무시)이면 그 앱으로 보낸다. 기본 앱도 이름(`-default-app`, 기본 `app`)으로 이 규칙에 들어 있으므로 `app.hopcharlie.dev`는 그대로 기본 앱이다.
- 도메인 아래의 모르는 이름은 404 `unknown_app`으로 답하고 어느 환경에도 보내지 않는다. 기본 앱으로 보내면 `shpo.hopcharlie.dev` 같은 오타가 다른 앱의 DB에 쓰기를 남긴다. 도메인 밖의 호스트(IP, 다른 도메인, 도메인 자체)는 지금처럼 기본 앱으로 보낸다.
- 앱 이름은 DNS 레이블 하나(`^[a-z0-9]([a-z0-9-]{0,30}[a-z0-9])?$`)다.
- 등록과 교체는 `PUT /apps/{app}`(환경 이름과 주소, 쓰기 환경, 읽기 비율)으로, 삭제는 `DELETE /apps/{app}`으로 한다. 그 앱의 쓰기를 보류하는 동안에는 둘 다 409 `writes_held`로 거부한다. 전환 중에 환경을 바꾸거나 앱을 지우면 붙잡은 쓰기가 어디로 갈지 엔진이 모르게 된다.
- 교체는 라우터를 새로 만들지 않고 그 자리에서 환경 목록과 라우팅을 바꾼다. 교체 전에 보낸 쓰기도 처리 중으로 남으므로, 바로 뒤에 온 hold가 그 쓰기를 기다린다. 이름과 주소가 그대로인 환경은 통계와 헬스 상태를 이어 간다.
- 앱별 관리 API는 `/apps/{app}` 아래에 `/v1` API를 그대로 둔다(`/apps/{app}/healthz`, `/apps/{app}/v1/state`, `/apps/{app}/v1/writes/hold` 등). 그래서 `<관리 주소>/apps/<app>`을 게이트웨이 주소로 주면 엔진의 HTTP 클라이언트와 `gateway.Client`가 고치지 않고 그 앱을 다룬다. `Client.App(name)`은 이 주소를 쓰는 클라이언트를 돌려준다. 앱 관리 요청과 앱별 요청은 모두 같은 관리 토큰을 요구한다.
- 상태 파일은 하나로 둔다. 기본 앱은 지금 형식 그대로 최상위에, 등록한 앱은 `apps`에 환경 주소와 함께 쓴다. 저장할 때마다 모든 앱의 지금 상태를 읽어서 쓰므로, 나중에 쓴 파일이 먼저 쓴 파일보다 오래된 상태를 담지 않는다. 등록한 앱도 기본 앱과 같은 규칙으로 되살린다. 보류는 release까지 이어지고, 맞지 않는 상태(없는 쓰기 환경, 합이 100이 아닌 비율, 잘못된 이름)는 추측하지 않고 시작을 거부한다.
- 지표는 기본 앱만 기존 이름과 라벨을 쓰고, 등록한 앱은 `charlie_gateway_app_*`에 `app` 라벨을 맨 앞에 붙인다. 기존 지표에 `app` 라벨을 더하면 `sum by (backend)` 같은 기존 쿼리와 대시보드가 여러 앱을 합쳐 버린다.

## 검토한 대안

- 앱마다 게이트웨이 프로세스 하나: 격리는 확실하지만 앱이 늘 때마다 Deployment, PVC, ALB 규칙이 늘고, 플랫폼이 배포할 때마다 infra를 고쳐야 한다.
- 모르는 호스트도 기본 앱으로 보내기: 설정 실수에 너그럽지만 오타가 다른 앱의 환경에 닿는다.
- 경로 접두사로 앱 고르기(`/shop/...`): 앱이 접두사를 알아야 하고, 쿠키와 절대 경로 링크가 깨진다.
- 앱마다 상태 파일 하나: 파일 하나에서 기본 앱 형식을 지키는 편이 PVC와 `-state-file`을 바꾸지 않는다.
- 교체할 때 라우터를 새로 만들어 바꿔 끼우기: 단순하지만 바꾸기 전에 보낸 쓰기를 새 라우터의 hold가 세지 않아, hold가 200을 준 뒤에도 그 쓰기가 원본에 들어갈 수 있다.

## 결과

- infra의 Helm 차트는 고치지 않아도 지금처럼 동작한다. 호스트 라우팅을 켜려면 게이트웨이에 `GATEWAY_APP_DOMAIN=hopcharlie.dev`를 넣는다. ALB가 `api`, `console`처럼 따로 잡은 호스트는 게이트웨이까지 오지 않으므로 그 이름으로 등록한 앱에는 닿지 않는다.
- 플랫폼(`internal/runs`)은 지금처럼 기본 앱만 이전한다. 등록한 앱을 플랫폼 API로 이전하려면 Plan 정책이 `gateway.url`로 `<관리 주소>/apps/<app>`을 받고, 카나리와 관찰이 그 앱의 클라이언트(`Client.App`)를 쓰게 바꿔야 한다.
- 새 게이트웨이가 쓴 상태 파일을 예전 게이트웨이가 읽으면 기본 앱은 그대로 이어지지만, 다음 저장에서 `apps`가 사라진다. 바이너리를 되돌렸다면 앱을 다시 등록한다.
- 등록한 앱의 헬스 체크도 `-health-path`를 쓴다. 그 경로가 없는 앱은 환경이 모두 unhealthy로 보이고, 읽기가 비율과 관계없이 쓰기 환경으로 간다.
- 앱을 지우고 같은 이름으로 바로 다시 만들면, 지우기 전에 보낸 쓰기는 새 앱의 hold가 기다리지 않는다. 삭제는 이전 흐름에 들어 있지 않다.
- 앱 요청과 응답 형식(`AppSpec`, `AppInfo`, `AppList`)은 `internal/gateway`에 있고, `api/openapi.yaml`에는 아직 넣지 않았다.
- 게이트웨이는 여전히 한 대라서, 이제는 모든 앱의 단일 장애점이다.
