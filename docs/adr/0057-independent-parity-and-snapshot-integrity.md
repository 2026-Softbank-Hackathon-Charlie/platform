# 0057. 독립 동등성 검사를 병렬 실행하고 파일 검사는 동일 스냅샷의 무결성으로 연결한다

- 상태: 채택
- 날짜: 2026-11-08

## 상황

동등성 검사의 5개 capability는 서로의 결과를 사용하지 않는데 순차 실행됐다. Gate 전체의 30초 제한 안에서 앞 검사의 지연이 뒤 검사의 실행 기회까지 줄였다.

파일 보호 경로는 매번 새 소스 스냅샷을 내려받아 내용을 검사한다. 이후 정책 승인 뒤 같은 스냅샷에 대해 정규식 검사와 ZIP 압축 해제를 다시 수행했다. 다운로드도 정렬용 256개 청크마다 rclone 프로세스를 다시 실행해 연결을 재사용하지 못했다. ADR 0053의 전송 병렬화와 전체 바이트 검증은 이미 main에 반영됐다.

## 결정

- 고정된 5개 capability를 병렬 실행한다. 개별 30초 context, 전체 Gate 제한, 필수 항목 실패·미상에 대한 `Passed=false` 판정, 관측 신선도와 결과 순서를 보존한다. 기존 audit 모드를 강제 차단 모드로 바꾸지 않는다. 모든 probe 종료를 기다린 뒤 보고서를 반환한다. 동일 인스턴스를 여러 capability에 등록하는 probe 구현은 동시 호출에 안전해야 한다.
- 검증된 inventory를 메모리에 모으지 않고 literal 파일 목록으로 디스크에 기록한 뒤 단일 rclone 다운로드 세션을 사용한다. 10,000개 객체, 개별 16MiB, 합계 256MiB, 16개 worker, backlog 256, hard 전송 제한을 유지한다. rclone의 파일 목록도 최대 객체 수와 경로 길이로 한정된다.
- 최초 내용 검사에서 생성한 manifest의 SHA256을 승인 근거로 유지한다. 승인 뒤에는 inventory·파일 목록 및 **모든 파일의 전체 바이트 SHA256**을 원래 manifest와 대조하고, manifest 자체도 원래 digest와 대조한다. 동일한 바이트에 대한 정규식·압축 해제의 두 번째 실행만 제거한다.
- 매 presync/delta/fence/Check마다 새 스냅샷과 최초 DLP 검사를 수행한다. 다른 단계·실행의 승인 근거를 캐시하지 않는다. 대상에는 계속 전체 스냅샷을 보내고 `check --download`로 전체 바이트를 확인한다.

## 검토한 대안

- 순차 capability 실행: 단순하지만 독립 네트워크 대기 시간이 합산된다.
- mtime/크기 또는 오래된 검사 보고서 재사용: 동일 크기 변조와 정책 변경을 놓칠 수 있어 제외했다.
- 대상 차이 목록만 업로드: 추가 대상 읽기와 삭제·불완전 목록 처리의 복잡성이 커 이번 변경에서 제외했다.
- DLP 두 번 실행 유지: 동일 바이트임을 확인해도 압축 해제·패턴 검사가 반복된다. 원래 manifest를 신뢰 앵커로 보존하는 전체 SHA256 대조를 선택했다.

## 결과

capability 동시 시작, 취소 후 모든 probe 종료, 보고서 순서, 기존 fail-closed 검사를 테스트한다. 파일은 승인 후 동일 크기 변조·추가·삭제, manifest 변조·잘림·추가 JSON, ZIP 내부 최초 DLP, 대규모 inventory의 단일 다운로드, 실제 로컬 rclone 변조 복구를 검증한다.

로컬 합성 ZIP fixture의 benchmark는 중복 DLP 비용과 SHA256 무결성 비용을 비교할 뿐 운영 개선율을 증명하지 않는다. 클라우드·온프레미스 간 실제 이전은 이 변경의 테스트로 수행하지 않았다. 운영 수치는 ADR 0053의 `timingMillis`를 배포 후 비교해야 한다. CNPG promotion, DB fence, 검증 표본과 승인 정책은 변경하지 않는다.
