# 0028. 쓰기 재시도 계약: 게이트웨이가 보내지 않은 쓰기는 다시 보내도 되고, 앱 쓰기는 클라이언트 키로 멱등이어야 한다

- 상태: 채택
- 날짜: 2026-11-06
- 관련: [0004 트래픽 게이트웨이](0004-traffic-gateway.md), migration-engine ADR 0013(쓰기 정지 시간 줄이기)

## 상황

이전 중 쓰기는 게이트웨이에서 잠시 보류된다. 보류 중이거나 그 직후 쓰기가 실패하는 경우가 실제로 있었다.

- 2026-11-05 운영 moimroom EKS → GKE 이전: 엔진이 halt한 3분 36초 동안 보류된 쓰기 9건이 55초 보류 한도를 넘겨 `503 hold_timeout`을 받았다. 부하기는 재시도하지 않아 9건이 실패로 남았다(커밋되지 않음, 누락 아님). migration-engine `docs/test-records/README.md`.
- 클라이언트가 응답을 받기 전에 연결이 끊기면, 쓰기가 커밋됐는지 클라이언트는 모른다. 같은 쓰기를 다시 보내면 두 번 들어갈 수 있다. 이전과 관계없이 일어나지만, 전환 직후처럼 연결이 흔들리는 때에 더 잦다.

플랫폼은 사용자 클라이언트를 바꿀 수 없다. 대신 게이트웨이가 어떤 실패를 "보내지 않았다"고 보장하는지와 앱이 어떻게 쓰기를 받아야 재시도가 안전한지를 계약으로 정한다.

## 결정

1. **게이트웨이가 백엔드로 보내지 않은 쓰기는 항상 다시 보내도 된다.** 아래 응답은 요청을 앱에 보내지 않았다는 뜻이고, `Retry-After: 1`을 붙인다.

   | 상태 | `error.code` | 언제 |
   |---|---|---|
   | 503 | `hold_timeout` | 보류된 쓰기가 최대 보류 시간(기본 55초)을 넘김 |
   | 503 | `too_many_held_writes` | 보류 줄이 가득 참 |
   | 503 | `shutting_down` | 게이트웨이 재시작 중 |

2. **그 밖의 5xx와 응답 없는 끊김은 커밋됐을 수도 있다.** 이때 재시도가 안전하려면 앱의 쓰기가 클라이언트가 정한 키로 멱등이어야 한다. 권장 형태는 클라이언트가 만든 id(또는 `Idempotency-Key`)에 유니크 제약을 두고 `INSERT ... ON CONFLICT DO NOTHING`처럼 같은 키의 두 번째 쓰기를 성공으로 답하는 것이다.
3. **게이트웨이는 쓰기를 스스로 재시도하지 않는다.** 백엔드가 응답 없이 끊겼을 때 커밋 여부를 게이트웨이도 모르기 때문이다(0004와 같음).
4. **E2E가 이 계약을 지킨다.**
   - 테스트 앱(`test/e2e/app`)의 `POST /items`는 id로 멱등이다.
   - 드라이버(`test/e2e/driver`)의 쓰기 사용자는 5xx와 끊김을 같은 id로 최대 6번 다시 보낸다. 503이면 1초, 그 밖은 0.3초 기다린다.
   - 시나리오 `lost-response`: 원본 앱이 5번째 쓰기마다 커밋한 뒤 응답 없이 연결을 끊는다. 실패 0건, 응답한 쓰기마다 정확히 한 행(중복 0, 클라이언트가 모르는 행 0)을 확인한다.

## 검토한 대안

- 게이트웨이에 `Idempotency-Key` 응답 캐시: 앱을 바꾸지 않고 중복을 막지만 게이트웨이는 한 대(0026)이고 메모리 캐시라 재시작에 사라진다. 커밋 여부를 모르는 끊김은 여전히 앱이 판단해야 한다. 앱 쪽 키가 더 확실하다.
- 최대 보류 시간을 늘리기: ALB 유휴 타임아웃(60초)과 Cloudflare 원본 대기(100초)보다 길게 잡을 수 없고, 길수록 사용자는 응답 없이 기다린다. 한도를 늘리기보다 보류 자체를 짧게 하고(엔진 ADR 0013) 넘친 쓰기는 재시도로 처리한다.
- 보류 한도를 넘긴 쓰기를 원본으로 보내기: 0004에서 기각했다. 원본이 강등된 뒤라 누락이 생길 수 있다.

## 결과

- 보류 한도를 넘겨 503을 받은 사용자는 재시도하면 실패를 보지 않는다. 그 쓰기는 앱에 간 적이 없으므로 중복도 없다.
- 응답이 끊긴 쓰기는 멱등인 앱에서만 안전하게 재시도된다. 운영 앱이 이 형태인지는 앱마다 확인해야 한다. moimroom의 예약 쓰기가 같은 키 재시도에 멱등인지는 아직 확인하지 않았다.
- 재시도는 사용자 지연을 늘린다. 실패를 숨기지 않도록 드라이버는 첫 시도 실패, 재시도로 끝난 쓰기, 재시도 횟수를 따로 센다.
