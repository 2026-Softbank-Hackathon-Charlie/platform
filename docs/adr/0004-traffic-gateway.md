# 0004. 트래픽 게이트웨이는 Go로 직접 만들고, 쓰기 보류와 읽기 가중치를 따로 다룬다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

사용자 요청은 Cloudflare Tunnel을 거쳐 클러스터 밖의 게이트웨이로 들어온다. 이전 엔진은 전환할 때 게이트웨이에 세 가지를 요구한다. 새 쓰기를 붙잡고 처리 중인 쓰기가 끝나기를 기다리기(hold), 대상 환경으로 트래픽 돌리기(route), 붙잡은 쓰기를 내보내기(release)다. 팀 문서에는 Envoy, HAProxy, Caddy, Go 직접 구현이 후보로 올라 있었다.

## 결정

- Go 표준 라이브러리의 `httputil.ReverseProxy`로 직접 만든다(`cmd/gateway`, `internal/gateway`).
- 요청을 읽기(GET, HEAD, OPTIONS)와 쓰기(그 밖의 메서드)로 나눈다.
  - 쓰기는 항상 writeBackend 한 곳으로만 보낸다. DB의 쓰기 주체가 하나라는 원칙을 게이트웨이에서도 지킨다.
  - 읽기는 readWeights 비율대로 나눈다. 카나리 단계에서 대상 환경으로 읽기 일부를 보내는 데 쓴다.
- hold는 새 쓰기를 대기시키고, 처리 중인 쓰기가 0이 된 뒤에 200을 돌려준다. release는 대기 중인 쓰기를 그 시점의 writeBackend로 보낸다. 그래서 엔진이 hold, route, release 순서로 부르면 붙잡힌 쓰기는 모두 새 환경으로 간다.
- hold는 원자적이다. 처리 중인 쓰기가 drain 시간 안에 끝나지 않거나 호출한 쪽이 떠나면, 게이트웨이가 스스로 보류를 되돌리고 504를 돌려준다. 엔진은 hold가 2xx로 끝났을 때만 보류 중이라고 기록하고, 실패한 hold에는 release를 부르지 않기 때문이다. drain하는 사이에 release가 들어오면 409를 돌려준다.
- 처리 중인 쓰기는 클라이언트가 연결을 끊어도 백엔드가 답할 때까지 센다. 클라이언트가 떠났다고 요청을 취소하면 백엔드는 트랜잭션을 계속 커밋하는데 게이트웨이는 끝났다고 보게 되고, 그 쓰기가 fence LSN 뒤에 원본에 들어갈 수 있다.
- 보류 자체는 release가 올 때까지 끝나지 않는다. 대신 쓰기 요청 하나가 최대 보류 시간(기본 90초)보다 오래 기다리면 그 요청에만 503과 Retry-After를 돌려주고, 백엔드로는 보내지 않는다. Cloudflare는 원본 응답을 약 100초까지만 기다리므로 그보다 오래 붙잡아도 사용자는 524를 받는다. 넘으면 현재 writeBackend로 자동 해제하고 지표에 남긴다. 플랫폼이나 엔진이 죽어도 사용자 쓰기가 무한히 멈추지 않게 하려는 것이다.
- writeBackend, readWeights, 보류 여부는 상태 파일에 저장한다. 게이트웨이를 재시작해도 보류 중이었다면 보류를 이어 간다.
- 쓰기는 대상의 헬스 체크가 실패해도 다른 곳으로 넘기지 않는다. 쓰기를 어디로 보낼지는 이전 엔진만 정한다. 읽기는 헬스 체크가 실패한 환경을 건너뛴다.
- 환경별 요청 수, 오류 수, p50/p95/p99를 1초 단위로 5분간 들고 있다가 `/v1/state?window=`로 내준다. 플랫폼은 이 값으로 카나리 게이트를 판정하고, 이전 중 실패 요청 수를 센다. 같은 값을 Prometheus `/metrics`로도 내보낸다.

## 검토한 대안

- Envoy: 가중치 라우팅과 지표는 기본으로 있다. 그러나 "쓰기만 붙잡았다가 새 백엔드로 흘려보내기"는 Lua나 ext_proc 필터를 따로 짜야 하고, 엔진이 부를 관리 API도 따로 만들어야 한다.
- HAProxy, Caddy: 가중치와 drain은 되지만, 메서드별로 요청을 대기시키는 기능이 없다.
- DNS 전환: TTL 때문에 전환 시점을 통제할 수 없고 쓰기를 붙잡을 수도 없다. 팀 문서에서도 제외했다.

## 결과

- 게이트웨이는 단일 장애점이다. 발표에서는 이 점을 한계로 밝히고, 상태 파일 기반이라 두 대로 늘리는 확장안을 설명한다.
- 처음에는 최대 보류 시간이 지나면 쓰기를 원본으로 풀었다. 리뷰에서 이 방식은 fence gate를 통과한 뒤 원본이 강등되기 전 사이에 쓰기가 원본에 들어가 누락될 수 있다는 점이 확인되어 바꿨다. 지금은 가용성보다 누락 0건을 택한다. 전환이 90초를 넘기면 그 사이 쓰기는 실패하지만 잃지는 않는다.
- 플랫폼이나 엔진이 보류 중에 죽으면 보류는 풀리지 않는다. 운영자가 상태를 확인하고 run을 재개하거나, 게이트웨이 관리 API의 `/v1/writes/release`를 직접 호출한다.
- 게이트웨이를 끌 때 대기 중인 쓰기에는 503을 돌려주고, 보류 상태는 파일에 남긴다.
- 클러스터 안에서 직접 DB에 쓰는 배치 작업은 게이트웨이가 막지 못한다. 이전 중에는 멈춰야 한다(엔진 문서와 같다).
