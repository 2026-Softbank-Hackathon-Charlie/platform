# 0005. 실행을 동기화, 읽기 카나리, 전환 승인, 전환 단계로 나눈다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

첫 버전은 승인된 Plan을 받으면 엔진의 9단계를 한 번에 끝까지 실행했다. 팀 문서는 두 가지를 더 요구한다. 하나는 전환 전에 사람이 승인하는 것이고, 다른 하나는 트래픽 비율을 단계적으로 올리면서 게이트를 통과해야 다음으로 가는 것이다. 엔진에는 단계를 하나씩 실행하는 `RunStep`이 있으므로, 엔진을 고치지 않고 플랫폼에서 단계를 끊어 부를 수 있다.

## 결정

실행 하나는 다음 순서로 진행한다.

1. 동기화(sync): precheck, prepare, presync, delta를 `RunStep`으로 하나씩 부른다. 사용자는 계속 원본을 쓴다.
2. 읽기 카나리(canary, 선택): 게이트웨이의 읽기 비율을 대상 환경으로 예를 들어 10%, 50% 순서로 올린다. 각 단계가 끝날 때 그 단계 동안 대상이 받은 요청으로 게이트를 판정한다(최소 요청 수, 오류율, p95). 하나라도 실패하면 읽기를 모두 원본으로 돌리고 `rolled_back`으로 끝낸다. 게이트웨이에 연결할 수 없으면 통과가 아니라 실패로 본다.
3. 전환 승인(awaiting_switch): 데이터가 따라잡힌 상태로 운영자의 `/switch`를 기다린다. 기다리는 동안에도 복제는 계속 흐른다. `autoSwitch`를 켜면 이 단계를 건너뛴다.
4. 전환과 검증(cutover, verify): fence부터 finalize까지도 `RunStep`으로 한 단계씩 부른다. 원복 경계(승격 요청 전에는 자동 원복, 후에는 정지)는 엔진이 지킨다.

엔진 상태는 엔진을 실행하는 goroutine에서만, 단계와 단계 사이에서만 읽는다. 엔진의 `State()`는 단계 기록을 공유하는 얕은 복사를 돌려주므로, 단계가 도는 중에 다른 goroutine에서 읽으면 data race가 생긴다(리뷰에서 실제 엔진으로 재현했다). 단계가 도는 동안 화면에 보이는 단계 상태는 step_started, step_succeeded, step_failed 이벤트로 갱신한다.

카나리가 읽기 비율을 바꾼 뒤에 run이 전환 없이 끝나면(실패, 중단, 재시작, 게이트 실패) 읽기를 모두 원본으로 되돌린다. 승격을 요청한 뒤 멈춘 `halted`는 사람이 판단하도록 그대로 둔다.

운영자는 언제든 `/abort`를 부를 수 있다. 쓰기 보류 전이면 바뀐 것이 없으므로 `aborted`로 끝나고, 그 뒤에는 엔진의 경계를 따라 `rolled_back` 또는 `halted`가 된다.

서버를 끌 때는 카나리 단계나 전환 승인을 기다리는 run을 바로 `interrupted`로 끝낸다. 엔진 단계를 실행 중인 run은 그 단계가 끝날 때까지 기다리고, 그 뒤에 기다림 단계로 들어가면 역시 `interrupted`로 끝낸다. 서버가 재시작되면 실행 중이던 run은 `interrupted`로 표시하고 자동으로 이어 가지 않는다. 쓰기 보류 중에 서버가 죽었다면 게이트웨이의 최대 보류 시간이 사용자를 보호하고, 운영자가 상태를 보고 `/resume`을 부른다. 재개하면 이미 끝난 단계는 건너뛴다.

## 검토한 대안

- 카나리를 쓰기까지 포함해 비율로 나누는 방식: CNPG는 쓰기 주체가 하나다. 대상 DB는 승격 전까지 읽기 전용이라 쓰기를 대상에 보내면 실패한다.
- 엔진에 카나리와 승인 대기 단계를 넣는 방식: 엔진 레포의 단계 목록과 상태 형식이 바뀐다. 엔진은 데이터 이전의 결정적 실행에만 집중하게 두는 것이 역할 경계상 낫다.
- 재시작 후 자동 재개: 전환 도중에 죽었다면 사람이 원인을 보기 전에 다시 보류와 승격을 시도하게 된다. 재개 버튼 하나를 누르는 비용이 더 싸다.

## 결과

- 카나리 동안 대상의 읽기는 복제 지연만큼 오래된 데이터를 볼 수 있다. 복제 지연이 1초 안팎이라 데모에는 문제가 없지만, 자기가 방금 쓴 글을 바로 읽어야 하는 화면에는 맞지 않는다.
- 이벤트에는 엔진 이벤트 외에 status_changed, canary_step, gate_result가 추가된다. 콘솔과 CLI는 이 이벤트로 진행 상황을 그린다.
- 결과표(`/v1/matrix`)는 환경 쌍마다 마지막으로 끝난 run의 다운타임, 실패 요청 수, 누락 수를 보여 준다.
