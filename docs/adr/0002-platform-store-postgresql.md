# 0002. 플랫폼 기록은 PostgreSQL에 두고, 엔진 상태 파일은 그대로 둔다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

첫 버전은 Plan과 실행 목록을 메모리에만 두었다. 서버를 재시작하면 목록이 사라졌고, SSE 이벤트에는 번호가 없어서 재접속한 클라이언트는 그 사이 이벤트를 잃었다. 6개 경로 결과표와 감사 로그도 남길 곳이 없었다.

## 결정

- 플랫폼 DB로 PostgreSQL을 쓴다. 테이블은 plans, runs, run_events, audit_log, idempotency_keys 다섯 개다.
- runs는 `apiv1.Run` 문서를 jsonb로 통째로 저장하고, 조회에 쓰는 상태와 환경만 컬럼으로 뽑는다. 실행 문서는 단계가 바뀔 때마다 모양이 달라지는데, 이것을 정규화하면 얻는 것보다 고칠 곳이 많다.
- run_events의 seq(bigserial)를 SSE id로 쓴다. 이벤트를 저장한 다음에 구독자에게 보내므로, Last-Event-ID로 재접속하면 빠진 이벤트를 모두 다시 받는다.
- Plan 상태 전이는 `UPDATE ... WHERE status = ANY(...)` 한 번으로 한다. 두 운영자가 동시에 시작을 눌러도 하나만 이긴다.
- 엔진의 상태 파일(`.hopcharlie/runs/<id>.json`)은 그대로 둔다. 엔진이 재개할 때 읽는 것은 이 파일이다. 플랫폼 DB는 플랫폼이 보여 주고 판단하는 데 쓰는 기록이다.
- 스키마 변경은 `internal/store/migrations`의 SQL 파일로 하고, 서버가 시작할 때 advisory lock을 잡고 적용한다.

## 검토한 대안

- SQLite: 설치가 필요 없지만, 관리 호스트가 바뀌거나 API를 두 개 띄우면 파일을 공유하기 어렵다. 팀 문서에서 실행 상태 DB를 PostgreSQL로 정해 두었다.
- 엔진 상태를 DB에 직접 저장하도록 엔진을 고치는 방식: 상태를 한 곳에 모을 수 있지만, 엔진 레포의 공개 계약을 바꿔야 하고 엔진 CLI 단독 실행이 어려워진다.

## 결과

- 서버를 재시작하면 실행 중이던 run은 `interrupted`로 표시되고, 운영자가 `resume`으로 이어 간다. 자동으로 이어 가지 않는 이유는 0005에 적었다.
- 엔진 상태 파일과 DB 문서가 잠깐 어긋날 수 있다. 화면에 보이는 엔진 상태는 이벤트가 올 때마다 엔진에서 다시 읽어 저장하므로, 어긋나는 시간은 이벤트 한 번 사이다.
- 플랫폼 DB가 죽으면 API가 멈춘다. 진행 중인 엔진은 영향을 받지 않고, 이벤트 저장만 실패로 로그에 남는다.
