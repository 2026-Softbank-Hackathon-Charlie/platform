# 0032. 계획을 승인할 때 원본 DB가 API가 실행되는 곳에서 닿는지 먼저 본다

- 상태: 제안
- 날짜: 2026-11-06
- 관련: [0011 preflight 코어](0011-preflight-core.md), [0020 PostgreSQL 메이저 버전 검사](0020-pg-major-version-gate.md), [이슈 #84](https://github.com/2026-Softbank-Hackathon-Charlie/platform/issues/84), infra #98, #99

## 상황

2026-11-06에 콘솔에서 시작한 moimroom 이전이 같은 이유로 거듭 멈췄다. 13:25, 15:17, 16:11, 16:35, 17:06의 다섯 번 모두 엔진의 `precheck`가 28~64ms 안에 이렇게 실패했다.

```text
source db: ping moimroom-db-gke-rw.moimroom.gke.ts.net:5432: ... lookup ... on 172.20.0.10:53: no such host
```

`172.20.0.10`은 API가 실행되는 관리 EKS의 클러스터 DNS이고, `*.ts.net`은 tailnet에 붙은 기기에서만 해석된다. 계획은 이 이름이 풀리는 곳(AI 러너의 샌드박스, tailnet에 붙은 기기)에서 만들고, 실행은 API가 있는 곳에서 한다. 그래서 계획과 리허설을 통과해도 실행 위치에서는 이름을 모를 수 있다.

- 리허설은 대상 클러스터 한 곳의 샌드박스에서 합성 데이터로 돈다. API 위치의 DNS와 네트워크는 보지 않는다(ai-sandbox 설계 문서 7장 "다루지 않는 것").
- 시작 전 검사의 `pgversion`과 `capacity`는 DB를 읽지 못하면 `unknown`으로 기록하고 막지 않는다([0020](0020-pg-major-version-gate.md), [preflight README](../../internal/preflight/README.md)). 이름이 풀리지 않아도 "시작 전 검사 ✓"로 지나간다. 17:06의 실행은 콘솔에 "시작 전 검사 ✓"가 표시된 뒤 엔진 `precheck`가 위 오류로 멈췄다.
- **길이 열린 뒤에도 같은 단계에서 다음 문제가 드러났다.** #99가 머지(17:15)돼 카탈로그가 `db-gke.hopcharlie-db-network.svc.cluster.local`로 바뀐 뒤, 17:24의 실행은 이름 해석과 TCP 연결을 통과하고 로그인에서 멈췄다: `failed SASL auth: FATAL: password authentication failed for user "app" (SQLSTATE 28P01)`. 이것도 시작한 뒤 엔진 `precheck`에서야 알게 됐다.
- 콘솔의 "승인하고 시작"은 한 번에 승인과 시작을 한다. 그래서 막힘이 실패한 run과 "이어서 실행할 수 있습니다" 안내로만 남는다. 같은 계획을 이어서 실행해도 같은 주소로 다시 실패한다.

## 결정

1. **`plans.Service.Approve`에서 원본 DB의 도달 가능 여부를 본다.** 새 패키지 `internal/preflight/reach`가 계획의 `source.dsn`에서 호스트와 포트를 읽어, 이름 해석(DNS)과 TCP 연결을 API가 실행되는 위치에서 시도하고, 연결되면 원본에 한해 그 DSN의 사용자로 로그인해 본다(세션을 열었다 바로 닫는다, `application_name`은 `hopcharlie-reach-preflight`). 시간은 한쪽 끝마다 4초로 묶는다. 대상에는 로그인하지 않는다.
2. **원본만 판정한다.** 대상 DB는 아직 없을 수 있다(엔진이 manifest로 만든다). 대상 결과는 기록용이고 막지 않는다.
3. **명백한 경우만 막는다.** 이름이 없다는 응답(`dns`), 해석된 주소 어디에도 연결이 열리지 않음(`tcp`), 로그인이 비밀번호 틀림(SQLSTATE 28P01)이나 접근 거부(28000, `pg_hba.conf` 거부 포함)로 거절됨(`auth`)이 그렇다. 해석기의 시간 초과나 오류, 호스트를 읽을 수 없는 DSN, 로그인이 그 밖의 이유로 실패한 경우(시간 초과, TLS, 접속 수 초과, DB 기동 중), 호출자가 포기한 경우는 `unknown`이고 승인한다. `pgversion`과 같은 원칙이다.
4. **막으면 409 `db_unreachable`이고 계획은 승인 대기로 남는다.** run이 만들어지지 않는다. 같은 경로가 생기면 같은 계획을 다시 승인할 수 있다. 카탈로그의 `dbHost`를 바꿨다면 계획이 만들 때의 `dbHost`를 복사해 두므로 새 계획이 필요하다.
5. **응답과 감사 기록에는 상태와 이유 코드만 담는다.** 호스트 이름, DSN, 서버 메시지는 넣지 않는다(`capacity`, `pgversion`과 같다).
6. **기본은 켜짐이고 `PLATFORM_REACH_GATE=off`로 끈다.**

## 하지 않는 것과 한계

- **시작(`Reserve`)과 재개는 바꾸지 않는다.** 승인 뒤에 경로가 사라지면 엔진 `precheck`가 그대로 막는다.
- **이름, 연결, 로그인까지만 본다.** 로그인 뒤의 SQL 권한과 복제 권한, 쓰기 가능 여부는 보지 않는다. 로그인이 되어도 이전이 끝까지 되는 것은 보증하지 않는다.
- **로그인은 비밀번호가 맞는지만 알려 준다.** 카탈로그의 `passwordEnv`가 다른 클러스터의 비밀번호를 담고 있거나, 경로가 의도하지 않은 DB로 이어져도 둘 다 `auth`로 보인다. 어느 쪽인지는 이 검사가 가리지 못한다.
- 승인할 때마다 원본에 짧은 세션 하나를 연다. 엔진 `precheck`와 `pgversion`이 시작할 때 하는 접속과 같은 종류이고 읽기만 한다.
- API pod 한 곳에서 본 결과다. 시작할 때 다른 pod에서 같은 결과가 나온다는 보증은 없다.
- 이미 승인된 계획은 다시 보지 않는다. 이 변경 이전에 승인한 계획도 그렇다. 롤백 계획은 승인 대기를 거치지 않고 만들어지므로 대상이 아니다.
- 연결 거부가 일시적이면 승인이 한 번 막힐 수 있다. 다시 승인하면 된다.
- "이어서 실행할 수 있습니다" 안내 문구는 콘솔(frontend)의 일이라 이 변경에 포함하지 않았다.
- 이 변경은 이전을 되게 만들지 않는다. 관리 EKS에서 DB로 가는 경로 자체는 infra #98, #99가 만든다. 이 검사는 그 경로가 없을 때 이전을 시작하기 전에 알려 줄 뿐이다.

## 검토한 대안

- **시작(`Reserve`)에서만 검사하기:** 엔진 `precheck`가 이미 같은 일을 하고, 그때는 run이 이미 실패로 남는다. 목적은 승인 전에 알리는 것이다.
- **`POST /v1/plans/draft` 응답에 결과 담기:** AI가 계획 단계에서 알 수 있어 좋지만 API 계약이 바뀌고 응답 모양을 따로 정해야 한다. 이 변경이 안정되면 후속으로 검토한다.
- **대상도 막기:** 대상이 아직 없는 계획이 정상이므로 막으면 안 된다.
- **`pgversion`, `capacity`를 읽지 못하면 막기:** 읽지 못함은 권한이나 일시 오류일 수 있어 막는 근거가 못 된다. 각 검사의 원칙을 바꾸지 않았다.

## 결과

- 오늘과 같은 상황(`*.ts.net` 이름이 관리 EKS에서 풀리지 않음)이 승인 단계에서 409로 드러나고, 실패한 run과 헷갈리는 "이어서 실행" 안내가 남지 않는다.
- 새 오류 코드 `db_unreachable`이 승인 응답에 생긴다(이유 코드는 `dns`, `tcp`, `auth`). 기존 응답은 바뀌지 않는다.
- 실제 배포에서의 동작(관리 EKS의 DNS, 프록시 경유 연결)은 이 변경으로 검증하지 않았다. 단위 테스트와 API 테스트는 이름 해석과 연결을 가짜로 바꿔서 본다.
