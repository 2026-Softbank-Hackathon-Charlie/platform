# 0010. 샘플 앱 moimroom으로 이전 전체를 로컬 kind에서 돌리는 E2E를 둔다

- 상태: 채택
- 날짜: 2026-11-02

## 상황

`test/e2e`는 단순한 테스트 앱으로 플랫폼, 게이트웨이, 엔진이 맞물리는지 확인한다. 하지만 실제 앱이 가진 것, 곧 Helm 차트, 커넥션 풀, 앱 스키마, 오브젝트 스토리지의 파일은 들어 있지 않았다. 그래서 파일 이전과 decommission이 실제 앱에서 동작하는지 확인한 적이 없었다. 본선 데모 대상인 샘플 앱 moimroom으로 이전의 처음부터 끝까지를 돌릴 수 있어야 했다.

## 결정

- `test/e2e/moimroom/`에 별도 E2E를 둔다. `run.sh` 한 번으로 kind 클러스터, CNPG DB 두 개, MinIO 두 개, moimroom Helm 릴리스 두 개를 띄우고, 사용자 부하 중에 플랫폼 API로만 이전한 뒤 엔진 CLI로 decommission까지 한다.
- 두 환경을 kind 클러스터 하나, 네임스페이스 하나에 둔다. 클러스터 두 개는 노트북에서 무겁고, 이 테스트가 확인하려는 것은 이전 절차이지 클러스터 사이 네트워크가 아니다.
- 파일은 환경마다 MinIO를 하나씩 두고 엔진이 rclone으로 옮긴다. 확인은 두 가지로 한다. 엔진의 rclone check 결과(`missingFiles`)와, 이전 뒤 게이트웨이를 거쳐 새 환경에서 받은 사진이 올린 것과 같은 크기인지다.
- 대상 DB와 대상 앱은 이전 전에 만든다. 실제 운영에서 infra가 대상 환경을 미리 만들어 두는 것과 같게 한다. 대상 앱은 읽기 전용 replica 위에서 떠야 한다.
- 이전은 카나리 10%·50%, 운영자 전환 승인, 전환 후 관찰(0009)을 모두 쓴다. 통과 조건은 run 성공, 누락 쓰기·파일 0, 기록한 예약이 새 primary에 전부 있음, 사진이 새 환경에서 나옴, decommission 통과다.
- decommission은 아직 플랫폼 API가 없어서 migration-engine에서 빌드한 `hopmigrate`로 실행한다. API가 생기면 바꾼다.
- moimroom과 migration-engine은 워크스페이스의 형제 체크아웃을 쓴다(`MOIMROOM_DIR`, `ENGINE_DIR`로 바꿀 수 있음). 이미지 레지스트리 없이 로컬에서 빌드해 kind에 올린다.
- Windows에서 빈 포트를 열 때 가끔 "invalid pointer address"(WSAEFAULT)로 실패한다. 원인을 찾지 못해 게이트웨이, API, 저장소 컨테이너 시작을 세 번까지 다시 시도한다.

## 검토한 대안

- 기존 `test/e2e`에 파일과 decommission 추가: 테스트 앱이 앱 스키마나 파일 업로드를 갖지 않아 실제 앱의 문제를 잡지 못한다. 실제로 moimroom E2E가 처음 잡은 두 문제(replica 위에서 앱 시작 실패, 종료 중 파드의 DB 세션)는 테스트 앱으로는 드러나지 않았다.
- 클라우드에서 실행: 비용과 시간이 들고 매번 돌리기 어렵다. 클라우드 리허설은 따로 한다.
- CI에서 실행: kind, 이미지 빌드, 부하까지 4~5분 이상 걸리고 러너 자원이 부족하다. 지금은 로컬에서 돌린다.

## 결과

- 로컬(Windows, Docker Desktop)에서 통과했다. 다운타임 15.3초, 게이트웨이 요청 4645건 실패 0, 누락 행·쓰기·파일 0, 예약 1224건과 사진 32장이 새 환경에 있음, decommission 통과.
- 이 테스트로 moimroom(replica에서 스키마 마이그레이션 건너뛰기)과 엔진(engine ADR 0011)을 고쳤다. 이 테스트는 두 수정이 들어간 체크아웃이 있어야 통과한다.
- 클러스터 사이 네트워크, TLS 이름, 클라우드 자원은 확인하지 않는다. 이 결과를 클라우드 이전의 증거로 쓰지 않는다.
