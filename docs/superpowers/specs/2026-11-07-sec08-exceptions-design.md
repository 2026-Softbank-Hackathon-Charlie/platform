# SEC-08: 발견 항목·취약점 예외 승인과 감사 — 설계

- 날짜: 2026-11-07 (해커톤 종료 2026-11-08, 하루 안에 끝나는 범위)
- 상태: 승인된 설계 (브레인스토밍 2026-11-07)
- 관련: ADR 0034, SEC-07 (KEV)

## 결정

| 항목 | 결정 |
|---|---|
| 범위 | 예외 등록·해제와 감사 기록만. 발견 항목 수명(처음/마지막 발견, 해결 판정)은 하지 않는다. |
| 승인 | operator 한 명이 사유와 만료일을 적어 바로 등록한다. agent(AI)와 viewer는 등록·해제할 수 없다. |
| 기간 | 만료일 필수, 등록 시점부터 최대 30일. KEV에 등재된 취약점은 최대 7일. |
| 만료 | 만료 시각이 지나면 예외가 붙지 않는다(자동으로 미처리로 보임). |
| 심각도 변화 | 무시. 기한 안이면 심각도가 바뀌어도 예외를 유지한다. |
| 대상 | 발견 항목(finding)과 취약점(vulnerability). 통제 평가는 제외. |
| 감사 | 등록·해제는 기존 감사 로그에 남는다(누가, 대상, 사유, 만료). |
| OCSF | 예외가 붙은 발견 항목은 status_id 3 Suppressed, status_detail에 사유. |
| 심각도 | 예외는 심각도를 바꾸지 않는다. |

## 데이터와 API (platform)

- 테이블 `security_exceptions` (migration 0013): id, target_type, target_id, reason, expires_at, created_by, created_at, revoked_at, revoked_by.
- 대상마다 활성 예외(해제 안 됨, 만료 전)는 하나뿐이다. 등록 시 활성 예외가 있으면 409.
- `GET /v1/security/exceptions` (viewer): 모든 예외(해제·만료 포함), 최신순.
- `POST /v1/security/exceptions` (operator): {targetType, targetId, reason, expiresAt} → 201. 사유 1~500자, 만료는 지금 이후이고 30일(KEV 등재 취약점은 7일) 이내. 취약점은 저장된 스캔에서 ID를 찾아야 하고(없으면 400), KEV 여부는 서버의 KEV 캐시로 판단한다(캐시가 없으면 30일 규칙).
- `DELETE /v1/security/exceptions/{id}` (operator): 해제 → 200. 없으면 404, 이미 해제됐으면 409.
- 보고서: `GET /v1/security`, `/ocsf`, `/vulnerabilities`는 활성 예외를 각 항목의 `exception` 필드로 붙인다. 예외 저장소를 읽지 못하면 예외 없이(=미처리로) 보고서를 돌려주고 로그를 남긴다.

## 화면 (frontend)

- 상세 패널(발견 항목, 취약점): 실데이터 모드에서 "예외 등록"(사유, 만료일; 기본 30일 뒤, KEV 등재면 최대 7일). 예외가 있으면 "예외 · MM/DD까지 · 등록자 · 사유"와 "예외 해제". 성공하면 다시 불러오고, 실패하면 서버 메시지를 그 자리에 보인다.
- 목록: 예외 행에 `예외 · 11/30까지` 칩과 흐린 표시. 필터 "예외": 제외(기본) / 포함 / 예외만. 우선순위 정렬에서 예외 그룹은 맨 뒤.
- 데모 모드에는 버튼이 없다.

## 테스트

- 저장소: 공통 conformance(등록, 활성 중복 409, 만료 후 재등록 허용, 해제, 이미 해제 409, 없는 id 404, 목록 최신순).
- API: 권한(viewer·agent 403), 30일·7일(KEV) 제한, 사유 검증, 없는 취약점 400, 보고서에 활성 예외만 붙음, 만료된 예외는 안 붙음, OCSF Suppressed, 감사 로그 기록.
- 화면: 칩, 필터 3종, 정렬 맨 뒤, 등록·해제 호출, 데모 모드 버튼 없음.
